# 23. プリペアドステートメントとSQLインジェクション対策

## 目的
文字列連結によるSQL構築の危険性（SQLインジェクション）を理解し、
プリペアドステートメント/パラメータバインディングで安全にクエリを実行できるようになる。

## 学習ポイント
- SQLインジェクションの仕組みと具体的な攻撃例
- プリペアドステートメント（`?`や`$1`などのプレースホルダ）とパラメータバインド
- 入力値のバリデーション・エスケープとの違い（プリペアドステートメントが本質的解決策であること）

## 推奨ライブラリ/ツール
- 21/22で使用したDBライブラリのプリペアドステートメントAPI

本課題では21番と同じ**SQLite3**（[third_party/sqlite3](../third_party/sqlite3/NOTICE.md)の
amalgamationを共有利用）を使う。DBはインメモリ(`:memory:`)で、実行の都度まっさらな
状態から数件のユーザーをシードする。

## 成果物イメージ
わざと文字列連結でSQLを組み立てた「脆弱な」実装と、プリペアドステートメントを
使った「安全な」実装を両方書き、攻撃文字列を入力して挙動の違いを確認する。

## ビルド方法・実行方法

他の課題と同様にCMakeを使う（詳細はルート [README.md](../README.md#cmakeとvisual-studioの使い分け) を参照）。

```sh
# 23_PreparedStatementSecurity ディレクトリで実行
cmake --preset x64-debug
cmake --build --preset x64-debug
./out/build/x64-debug/PreparedStatementSecurity
```

引数無しで実行すると、3種類の入力（通常のユーザー名/存在しないユーザー名/
SQLインジェクション攻撃文字列）それぞれについて、脆弱な実装と安全な実装の
結果を並べて表示する。

## 構成と学習ポイントとの対応

| 要素 | 内容 | 学習ポイント |
|---|---|---|
| `UserRepository::FindByUsernameUnsafe` | `"... WHERE username = '" + username + "'"`という文字列連結でSQLを組み立て`sqlite3_exec`で実行 | SQLインジェクションの仕組みと具体的な攻撃例 |
| `UserRepository::FindByUsernameSafe` | `?`プレースホルダ+`sqlite3_bind_text`でパラメータをバインド | プリペアドステートメント(プレースホルダ)とパラメータバインド |
| `src/main.cpp`の`RunCase` | 同じ入力をUnsafe/Safe両方に与え、結果を並べて表示 | 入力値のエスケープとの違い(構造と値の分離が本質的解決策であること) |

## 動作確認

ビルド・実行し、以下の3ケースで挙動を確認済み。

| 入力 | 脆弱(文字列連結) | 安全(プリペアドステートメント) |
|---|---|---|
| `alice`(通常) | alice 1件がヒット | alice 1件がヒット(同じ結果) |
| `nobody`(存在しない) | 該当なし | 該当なし(同じ結果) |
| `' OR '1'='1`(攻撃文字列) | **全ユーザー3件が漏洩**(WHERE句が`'' OR '1'='1'`になり常に真になるため) | 該当なし(usernameという文字列そのものとして扱われるため一致しない) |

攻撃文字列のケースで脆弱な実装だけが全ユーザーの情報（パスワードを含む）を
返してしまうこと、安全な実装は同じ入力でもSQLの構造が変化しないため
安全に「該当なし」として処理されることを確認した。これにより、
入力値のエスケープ処理を頑張るのではなく、プリペアドステートメントで
SQLの構造(命令)と値(データ)を最初から分離しておくことが本質的な対策で
あることが実演できている。
